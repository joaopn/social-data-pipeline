# The web UI

The web UI is a page in your browser for the pipeline of one deployment. It runs in a container of its own and does everything through the [broker](broker.md) and, for its Queue window, through the [query scheduler](../profiles/jobs.md)'s control socket: it holds no database password, no Docker access and no file of the deployment, only the broker's socket folder, its own certificate and, when they are there, the scheduler's control folder and results folder and the chat's socket folder. After the login you get the Management window: the **Overview** (the databases and whether they run, the configured sources with their profiles, the pipeline runs that are alive now, and standing notices for a database without authentication and for ports open beyond this machine) and the pages **Sources**, **Databases**, **Runs** and **System**, described below. The **Queue** window is the scheduler's queue and the **Chat** window the chat's assistant (both below). Reading a page changes nothing; every action is shown with its `sdp` command (or, in the Queue, with the query it acts on) and runs only once you confirm it.

It needs Linux and a Docker without user-id mapping: rootless Docker and `userns-remap` are refused, because the broker accepts connections only from the operator's own user id, and under such a mapping the container's connections arrive as another one.

## The pages

| Page | What it shows | What you can do there |
|------|---------------|-----------------------|
| **Sources** (`/sources`) | The configured sources and their profiles (`source list`) | Open a source |
| **A source** (`/sources/<name>`) | Its ingestion state (`source status <name>`: platform, data types, profiles, paths, the state files per database), the finished files per stage (`source progress <name>`), and the error logs of its profiles among `postgres_ingest`, `postgres_ml` and `mongo_ingest` (`source error-logs`; one too large for the page names the terminal command that prints it) | Run each of its profiles, one small form per profile with only that profile's options: rebuild the image (all), a file filter (all but `sr_ingest` and `sr_ml`), skip files with a lingua output (`parse`), one classifier (`ml`, `lingua`, `sr_ml`), the database admin password (the profiles that use a database; the form says whether one is kept for the session). Remove the source |
| **Databases** (`/databases`, one database at `/databases/<database>`) | Per database its state, ports, data folder and admin user (`db status`) and its checks (`db verify`); the MCP servers and the scheduler; the checks that are no database's | Start services (one of the services `db start` takes, or all; with the database admin password when one is needed), stop them (one or all), reset or remove a database, remove the MCP servers' or the scheduler's configuration, keep the database admin password for this session or forget it |
| **Runs** (`/runs`) | The runs, recorded ones (started from the web UI) and those started in a terminal that are alive now: kind, profile, source, state, start, end, exit code (`runs list`) | Open a run |
| **A run** (`/runs/<run id>`) | Its facts (the non-secret fields it was started with, who started it, its state) and its output, which follows the run as it goes (below) | Cancel it while it is alive |
| **System** (`/system`) | The broker's greeting (its protocol, whether a management password is set), the newest 200 lines of the broker's audit log (time, session, event, verb, outcome; a refused call with its code), and the table of what the web UI may ask the broker, with each entry's class and terminal command | Nothing |

Each block of a page is read on its own: a read that fails (a time-out, a state file that cannot be read, Docker out of reach) is shown as a sentence in its block, and the rest of the page stays. A name becomes a link only when it is a plain name (a letter or digit, then letters, digits, `_`, `.`, `-`, at most 64 characters); everything the broker hands over is shown as text.

## How an action is confirmed

1. A form (a button on one of the pages) sends what you chose. The web UI checks it against its own table of actions without asking the broker: only the fields that action takes, the closed choices, names of the plain form, a file filter of letters, digits and `_ . * ? [ ] ! -` (not only dots), and the rules of `run`: no file filter with `sr_ingest` and `sr_ml`, skipping lingua files only with `parse`, a classifier only with `ml`, `lingua` and `sr_ml`. A choice that does not pass is refused and nothing is kept or sent.
2. It is kept as a pending action of your session, and the page shows it: the `sdp` command it stands for (what you would type in a terminal; it never holds a password), every input (a password as dots), for an action that destroys something one sentence saying what it destroys and the name of what is destroyed, for a start or a stop what else the service chosen acts on (a database's MCP server, the scheduler, the database an MCP server needs; "every configured service" when none is chosen), and a field for the management password for the actions that need it again: a database start, a database reset, removing a database, the MCP servers' configuration or the scheduler's configuration, removing a source, and keeping the database admin password for the session. Starting and cancelling a run, stopping services and forgetting the database password need none. A terminal would also ask for the secrets the command does not show (the database admin password, a confirmation).
3. Confirm sends only that password, or nothing. The pending action is then taken out of the session, so a second confirm (a double click, another tab) finds nothing; it is passed to the broker once.
4. The action runs in the background, not tied to your request, with no time limit (a state-changing command can last many minutes). The confirmation waits up to two seconds for an answer: a refusal that comes at once is shown on the pending page (a wrong management password keeps the action, so you can type it again; five wrong ones end the session at the broker, and so here). Otherwise the outcome page says "under way" and looks again every two seconds, until it shows the exit code with the end of the command's output and errors, the link to the run that was started, or the refusal's sentence. A broker that cannot be reached is an outcome; it does not log you out.

At most two actions run at once from the web UI; a third is answered "busy" and stays pending. Cancelling a run has two places of its own, so that a cancel gets through while a database start or a reset runs for minutes. A run start and a database start use the database admin password kept for the session when their form leaves the field empty.

## The Queue window

The Queue window (`/queue`) is the query scheduler's own page, one to one, reached through the scheduler's control socket instead of the scheduler's port and password: the queries that agents submitted over the scheduler's MCP endpoint, waiting for a human approval. **Approving a query makes the scheduler run it on its database with the database's admin login**, not with the read-only login of the MCP servers. Treat every approval as running that statement yourself as the database's administrator.

| Page | What it shows | What you can do there |
|------|---------------|-----------------------|
| **Pending**, **Approved**, **Running**, **History** (`/queue?tab=...`) | The number of jobs in the first three tabs, and 50 jobs of the tab per page (the oldest first, the history newest first; "More" while there are more): each job's id (a link to its page), target and backend, the start of its statement, its description and its times; in the history its outcome, rows, size and its error or rejection reason. The Running tab refreshes itself every 5 seconds | Open a job |
| **A job** (`/queue/<job id>`) | Everything the scheduler's page shows of it: its phase and status, target, backend (for MongoDB the collection and database), output file (and whether it overwrites an existing result), times, rows and size, description, error or rejection reason, who approved or rejected it or asked to kill it through the web UI (`web-<n>`, the broker's number of the session), and its statement as the scheduler holds it, with its hints | Pending: approve, reject with a reason, EXPLAIN. Running: kill. Finished: preview the result and download each of its parts |
| **Auto-accept** (`/queue/auto-accept`) | Each target of the scheduler with its backend and database, whether auto-accept is on and its limit | Switch it on or off and set the limit, one form per target |

A job whose record is too large for the web UI (more than 1 MiB) is listed, but its page says to use the scheduler's own page, and it offers no approval.

A query that the [chat](chat.md)'s assistant submitted (its record carries `submitted_by: "assistant"`) is labelled "Submitted by the chat's assistant" wherever it is shown: in its row of each tab, on its page, and on the confirm pages of its approval, rejection, kill and EXPLAIN (for the last three the web UI reads the job when the action is chosen, after the broker's check, and keeps only whether it is the assistant's; a session the broker has ended goes to the login page and nothing is read). Any other value of that field, which only a hand-edited record can have, is shown as nothing. The approval's confirm page of such a query also says, above the statement: "The chat's assistant wrote this query, and text in the data it read can steer what it writes: read the statement as carefully as one from a stranger." The EXPLAIN confirm page of such a query says, above its own sentence: "The chat's assistant wrote this query, and text in the data it read can steer what it writes: an EXPLAIN of it runs before anyone approved it." When the job could not be read for a rejection, a kill or an EXPLAIN (the web UI busy, the scheduler refusing or not answering, a reply of another shape), its page says "Whether the chat's assistant submitted this query could not be read." and the action can still be confirmed; the EXPLAIN page then says that the query may have been written by the chat's assistant. What is kept and sent on confirm (the job's id, its digest, `web-<n>`) is the same as for any query. The auto-accept page says that the assistant's queries are never auto-accepted: the scheduler leaves each one waiting for a person, whatever the target's setting.

### How an approval is confirmed, and what the page does not check

The Approve button sends only the job's id. The web UI then reads the whole job from the scheduler and keeps it, with the scheduler's digest of what the job runs (its target, backend, statement, output file, overwrite, collection and database), as a pending action of your session. Its page shows the target and backend, for MongoDB the collection and database, the output file and "It overwrites an existing result of that name." when it does (for any true value of the record's `overwrite`, as the scheduler reads it; a value that is not `true` is shown beside it), the description, and the statement exactly as the scheduler holds it, whole, in a box without a height of its own, under a line with its number of lines and characters (the job's page has the same line above its box, which scrolls). Every character that would not show as itself is written as an escape (`\u202e` for a change of the text's direction, `\u200b` for an invisible space, `\u0000` for a control character, a line or paragraph separator, a private character), marked, and the page says how many it found; the line break and the tab are kept. A lone surrogate (half of a character, which a hand-edited record can hold) arrives as `?`: the scheduler replaces it before it sends. A statement that is not text (a record edited by hand) is shown as its JSON, the page says so, and no hints are computed for it. Below it are the **hints, not a check**: the words of a short list per backend that the statement holds, ignoring case (PostgreSQL: `PROGRAM`, `COPY`, `pg_read_`, `pg_ls_`, `pg_write_`, `lo_import`, `lo_export`, `dblink`, a `;` that is not the last character, a leading `ANALYZE` or `(` option list; StarRocks: `INTO OUTFILE`, `FILES(`, `INSERT`, `LOAD`, `SET`, a `;` that is not the last character; MongoDB: `$out`, `$merge`, `$function`, `$accumulator`, `$where`, also with the `$` written `\u0024`). Words count from a word's start (`OFFSET` does not hint `SET`); a PostgreSQL dollar quote does not hide a word (`$q$COPY ...$q$` hints `COPY`); comments before PostgreSQL's leading `ANALYZE` are skipped, nested block comments as PostgreSQL nests them. An empty list proves nothing. The page says that the query will run with the database's admin login, and that this page does not check the statement.

Confirming sends the approval with the digest kept from that page. The scheduler compares it with the job as it is at that moment: a job that was changed since is refused ("changed"), one that is no longer pending is refused with what it is now, and nothing is approved. A job approved through the web UI names `web-<n>` in the scheduler's record.

Every change of the Queue (approve, reject, kill, EXPLAIN, auto-accept) takes the Management window's way: a pending action, its page, the confirmation, an outcome page. Before the scheduler is asked, the web UI asks the broker whether your session still lives: a session the broker has ended (the management password was changed in a terminal, the broker was restarted) goes to the login page and the scheduler is not asked; a broker that cannot be reached refuses the change. A change whose request was sent and whose answer never came may have been done: its outcome says so and asks you to open the job (or the auto-accept page) again to see. The same is said when the request could not be delivered after the connection was made: the page cannot tell the two apart and says the cautious thing. A step before the change that fails (the session's check, the password's, the second look at auto-accept's settings) says that nothing was sent. A rejection's reason is at most 500 characters, without a line break or a control character, and is checked before anything is kept. A kill says whether the job was running; a job may still finish by itself before the database stops it. EXPLAIN is sent to the database with the database's admin login, before anyone approved the query, as the scheduler's own EXPLAIN button does: a statement written for it can execute, and the page says so. Its outcome shows the plan (its first 16 KiB) or the database's error text. An EXPLAIN that the database did not answer in time may still be running there, and a change the scheduler did not finish in time may still happen: the outcome says so.

### Auto-accept and the management password

With auto-accept on, the scheduler approves every query submitted to that target itself, up to the limit of the target's queries approved or running at a time, and each runs with the database's admin login without anyone looking at it; the pending page of switching it on says so. Switching auto-accept on for a target, or raising its limit, needs the management password again: the confirmation checks it at the broker before the scheduler is asked, and a wrong one keeps the pending action (five wrong ones end the session, as for any action). Switching it off or lowering the limit needs none. Only what you changed is sent; the web UI reads the target's settings again at the confirmation and refuses the change when they are no longer those its pending page showed as "Now" (another session changed them meanwhile), so that what is set is what the page's "After" line said. A target the scheduler does not have, and a limit above the scheduler's largest (the page names it), are refused before anything is kept.

### Previews and downloads

For a finished job the page has a Preview button: the scheduler reads at most 1 MiB of the first part of the result and sends at most 50 rows, which are shown as text, with the names and sizes of the parts and "truncated" when the first part is longer than what was read. The page also offers one download link per part; a part is addressed by its position among the parts (`/queue/<job id>/download/<n>`, counted from 0 in the order above), not by its name. The web UI reads the parts itself, from its read-only mount of the results folder, and only for a job the scheduler has in its history as done: the job's folder is opened without following a link, only files named like the job's output file (or `<name>_<number><extension>`) that are regular files are offered (a link, a folder or a FIFO with such a name is not), and the part is sent from the file it opened, as a download (`application/octet-stream`, its name reduced to letters, digits, `.`, `_` and `-`). At most two downloads run at a time; a third is answered "busy".

### What the window needs, and why it may not be there

- The scheduler set up (`python sdp.py db setup-jobs`, which makes `data/jobs` as you) and started with an image that has the control socket (`python sdp.py db start jobs`, which rebuilds it).
- The web UI started (`python sdp.py webui start`) after `data/jobs` exists. The start makes `data/jobs/control` (mode 0700) when it is missing and mounts it read-only into the container; it mounts the results folder (`JOBS_RESULT_ROOT` of `.env`, by default `data/jobs/results`) read-only for the downloads. It reads that key from the deployment's `.env` the way `sdp` reads it: a value written in quotes, or one overridden in the shell's environment when the scheduler was started, is not followed, and the downloads are then not available (or show nothing for a job). When `data/jobs` is not there, is a link or belongs to another user, or `data/jobs/control` is a link or belongs to another user, the start prints one line saying so and starts the web UI without the Queue's mounts; it prints one line when the results folder is missing, has a comma in its path, is `data/jobs` or a folder above it, or lies inside the control folder, and starts the web UI without downloads. `python sdp.py webui status` says which of the two folders are mounted. After fixing the reason, stop and start the web UI.

Each page of the window says why it cannot reach the scheduler: the folders were not there when the web UI started; the control folder is a link or not a folder, belongs to another user or is open to the group or others (then nothing is sent to it: `chmod 700 data/jobs/control`); something other than a socket of your user that only you may use is in the socket's place (a file, a link, a socket of another user or one open to others: nothing is sent to it); there is no socket (the scheduler is not running, or its image was built before it had one); nobody listens on it (the scheduler is not running); the web UI may not open it or the scheduler closed the connection without an answer (the web UI does not run as the user `data/jobs` belongs to). The scheduler's own page on its port is unchanged and keeps working.

Every page and part of the Queue window asks the broker first whether your session still lives (`audit.list` of one line), and believes its yes for 5 seconds; a download asks every time. A session the broker has ended goes to the login page, and a broker that cannot be reached shows its sentence: in both cases nothing is asked of the scheduler and no file is opened.

The Queue window's calls to the scheduler run apart from the Management pages, four at a time ("busy" beyond), with a time limit of 30 seconds for a read, 90 seconds for EXPLAIN and 75 seconds for any other change.

## The Chat window

The Chat window (`/chat`, the first entry of the window bar) is where you ask questions about the data and the [chat](chat.md)'s assistant answers. The assistant runs in the chat's sandbox container; the web UI talks to the chat's runner there through its socket (`.sdp/chat/socket/runner.sock`) and holds nothing of the chat itself: no credential, no file of the work folder.

| Page | What it shows | What you can do there |
|------|---------------|-----------------------|
| **Chats** (`/chat`) | The back end, the databases the assistant can read and whether it can submit queries to the scheduler's queue (the line "Query queue": attached, each query then waiting until a person approves it in the Queue window, or not attached); the chats, newest first, each with its title (the start of its first question), when it was started and whether a turn runs | Start a new chat, open one |
| **A chat** (`/chat/<id>`) | The conversation: your questions, the assistant's answers, each tool call and each tool result collapsed (open one to see its input or its text; a result that was an error is marked), each file a turn made or changed with a download link (and a PNG or JPEG image shown in the page), and at the end of each turn a line with how long it took and the cost the back end reported (Claude Code reports one, the `openai-compatible` back end none). While a turn runs, new events appear by themselves (the page asks every 2 seconds) and a Stop button is shown. One view shows at most 2,000 events and then a link "Continue from here", which opens the chat from that event on (`/chat/<id>?from=<n>`). Below: the chat's files with their download links | Send a question, stop the turn that runs, download a file, delete the chat |

A question is 1 to 32,000 characters. Send makes the sandbox start a turn and leads back to the chat, where the answer comes in as it is written; one turn runs per chat, and at most two in the whole sandbox. A question that is refused stays in the box with the reason: a turn of this chat still runs, two turns run already, the work folder is over its soft cap, or the chat's log is full (start a new chat). Stop ends the turn that runs; the conversation then says the turn was stopped. Delete asks first on a page of its own (which changes nothing) and then removes the chat and every file in its folder; a chat whose turn runs cannot be deleted until the turn has ended.

### Files and plots

The files are those in the chat's folder in the sandbox (what the assistant writes, such as a plot made with a shell command). A download is sent as an attachment (`application/octet-stream`), under its name with every character but letters, digits, `.`, `_` and `-` replaced by `_`, at most 1 GiB, two at a time, within 30 minutes; it is read through the runner's socket piece by piece, and if the file changes size while it is sent, or a piece before the end comes short, the download ends without the rest. An image is shown in the page only when the file's first bytes are those of a PNG or a JPEG (whatever its name says), at most 8 MiB, read within 30 seconds; any other file named `.png` is not shown. Only names of letters, digits, spaces, dots, dashes and underscores are listed or linked (the runner's own rule); a file with another name is in the work folder on this machine (`.sdp/chat/work`).

### Everything from the sandbox is shown as text

The code the assistant writes runs in the sandbox beside the runner, as the same user: it can replace the runner's socket and make it answer anything. So the page treats every answer as hostile. Before each connection it checks that the socket's folder and the socket are of your user and closed to everyone else, and sends nothing otherwise. An answer larger than the runner ever sends (1 MiB) is not read, and one holding more than 20,000 objects and lists is not parsed. Every answer must have exactly the shape the runner sends, numbers within their bounds and a page of events at most 512 KiB of text, as the runner sends (else the page says the sandbox answered something it does not understand, and shows nothing of it), and every event too (else one line says so). One page of events is shown as at most 100,000 pieces of text, blocks and list items: the first event beyond that is a line with a link that opens the chat from that event on, and the events after it on that page say they follow; an event too long to show even on its own is shown cut, with a line saying so. Every text is shown as text, with invisible and direction-changing characters as escapes such as `\u202e`. The assistant's answers are drawn by the page's own small renderer: paragraphs, headings, lists, quotes, code blocks, bold, italic and code; a link, an image or HTML in an answer is shown as its literal text, never followed or loaded. A tool's name is shown only when it is a plain name. File downloads and images carry `Content-Security-Policy: sandbox` and `nosniff`, so a browser never runs what is in them.

### What the window needs, and why it may not be there

- The chat set up and started (`python sdp.py chat setup`, `python sdp.py chat start`), which makes `.sdp/chat/socket` (mode 0700) and starts the sandbox that listens there.
- The web UI started after that folder exists. The start mounts it read-only at `/run/sdp-chat`; when it is not there, is a link (or a folder above it is), belongs to another user or is open to the group or others, the start prints one line saying the Chat window will not be available and why, and starts without it (`python sdp.py webui status` says whether it is mounted). Stop and start the web UI once the chat is set up.

The page says why it cannot reach the chat: the folder was not there when the web UI started; the folder or the socket fails its check (a link, another user's, open to others: nothing is sent); there is no socket or nobody listens on it (the chat is not running: `python sdp.py chat start`); or the sandbox closed the connection without an answer it can read. Every page, part, download and change of the window asks the broker first whether your session still lives (believed 5 seconds for a page or a part, asked again for every change, download and image): a session the broker has ended goes to the login page and nothing is asked of the sandbox. Sending, stopping and deleting need no management password: they change nothing outside the sandbox. The window's calls run four at a time ("busy" beyond), with a time limit of 10 seconds (30 for sending and deleting).

## The output of a run

The run page follows the run's output by itself. For a run started from the web UI the output is read from its log file in pieces of 64 KiB and appended, every 3 seconds while the run is alive and at once for the rest of a run that has ended; whole lines only are appended, and the unfinished last line is shown apart until its end arrives, so that colour codes and a progress bar that rewrites its line are cleaned as one line (a line longer than 64 KiB without an end is shown as it is). For a run started in a terminal, and for a recorded run whose supervisor is gone while its container still runs, the output is what Docker holds, its last 500 lines, read every 10 seconds and replacing what is shown. The pieces of all open views are read through four places of their own and Docker's tails through two, apart from the pages, so that open run pages cannot make the other pages busy; when those places are full, the view says it is busy and tries again in 10 seconds. A request for output the view has already shown (a stale tab) adds nothing and stops that view. The view stops when the run has ended and nothing more came, after one empty answer for a run that is lost or whose record cannot be read, and after 4 MiB in one view, where a link continues from that point in a fresh view (`/runs/<run id>?offset=<byte>`). Escape sequences, control characters and characters that change the direction of text are removed before the text is shown.

## What the web UI keeps in its memory

Nothing of this is written to a file, and restarting the web UI drops all of it.

| What | How long | How much |
|------|----------|----------|
| Your session: the broker's token, the form token | Until the logout, the broker's end of the session (at most eight hours) or a restart | 64 sessions; a new login beyond that drops the oldest |
| Pending actions, with a database admin password typed into a form, and for a Queue action its page made once (for an approval with the whole record of the job as the scheduler sent it) | Five minutes, or until confirmed | 16 per session, and at most 4 MiB together, counted with every run of escaped text at 128 bytes besides its characters; the oldest is dropped, and an approval that alone weighs more is not kept (its page says to use the scheduler's own page) |
| Outcomes of confirmed actions: the exit code and the end of the output and the errors; for the Queue what the scheduler answered (the start of an EXPLAIN's plan or error) | As long as the session, among its newest | 32 per session (finished ones are dropped before running ones), 16 KiB of each text |
| Output views: where each open run page reads next, and its unfinished last line | As long as the session | 8 per session (the oldest is dropped; its page then says so), 64 KiB held per view |
| Whether a database admin password was kept at the broker for the session (the password itself is kept by the broker only) | As long as the session | One flag |

So a session holds at most about 5.6 MiB: 1 MiB of outcomes, 512 KiB of unfinished lines and 4 MiB of pending Queue actions (records and their pages' runs, as counted); 64 sessions that each keep approvals of the largest jobs the scheduler sends could reach about 360 MiB of the container's 512 MiB. The management password typed again for an action is passed to the broker and kept nowhere.

## Commands

| Command | What it does |
|---------|--------------|
| `sdp.py webui setup` | Asks the port (default 8443), the listen addresses besides 127.0.0.1, the names the page is reached by besides `localhost`, and the certificate (generate one, or give the paths of your own certificate and key, which are copied). Refuses when no management password is set (`sdp.py broker passwd` first) and while the web UI's container exists. Builds the image `sdp-webui`, makes or copies the certificate, and prints its SHA-256 fingerprint and the addresses the page will answer on. |
| `sdp.py webui start` | Starts the container `sdp-webui` on its own network `sdp-webui` and says whether the broker answered from inside it (start the broker with `sdp.py broker start`; the page needs it to log in). Mounts the scheduler's control folder and results folder for the Queue window when they pass their checks, and prints one line for each that does not (see the Queue window). Mounts the chat's socket folder for the Chat window when it passes its check, and prints one line when it does not (see the Chat window). Says so with exit code 0 when it already runs. Refused when the web UI is not set up and under rootless Docker or user-id remapping. When Docker refuses (an address the machine does not have, a port in use), or the server ends right after its start (a certificate or key it cannot read), the container is removed, Docker's reason or the server's last lines are printed, and the exit code is 1. |
| `sdp.py webui stop` | Stops and removes the container. Exit code 1 when it was not running. |
| `sdp.py webui status` | Says whether it is set up and runs, whether the Queue window's two folders and the Chat window's socket folder are mounted, its port, listen addresses and names, the certificate's fingerprint and end date, and the addresses of the page. Exit code 0 when it runs, 1 when not. |
| `sdp.py webui unsetup` | Asks first, then removes the container, the network, the image and `.sdp/webui/`. |

The page answers at `https://localhost:<port>/` and `https://127.0.0.1:<port>/` on this machine, and at `https://<address or name>:<port>/` for each listen address and name you gave.

## Reaching it from another machine or a tailnet

By default the page is published on 127.0.0.1 only. To reach it from another machine, give `webui setup` the address of this machine on the network you want (a LAN address, or the address this machine has on a tailnet such as Tailscale) as a listen address, and the name you will type in the browser (a tailnet name, for example) as a name. Each address is published on its own; "every address" (`0.0.0.0`, `::`, `*`) is refused, because it would also answer on networks you did not choose. The page answers only to the names and addresses you gave: a request with any other `Host` is refused, which also stops a page of another site from reaching it by pointing a name of its own at your machine.

The container listens on two ports: 127.0.0.1 of this machine is published to its port 8444, every other listen address to its port 8443. A login is sent to the broker as `local` only with two signs: it arrived on 8444, and it comes from the address of the container network's gateway (as which Docker's proxy shows a client on 127.0.0.1). Any other login is `remote`. Each channel draws on the broker's budget of that name (five failed logins, one given back every 30 seconds), so that failed guesses from elsewhere never lock out a login at the machine itself. One sign is not enough: Docker's proxy can connect from the gateway for a client of any address on 8443, and a machine that routes to the container's network through this one may reach 8444 directly with its own address. "Local" therefore means anyone on this machine who can reach 127.0.0.1, other accounts of the machine included. Where Docker's proxy is switched off for loopback traffic, a login at the machine itself counts as coming from elsewhere, which is the safe direction. Loopback addresses (`::1`, `127.0.0.2`, ...) are not taken as listen addresses: the machine itself is served on 127.0.0.1.

Besides, the web UI limits each client address (an IPv6 address by its /64; every local login counts as one address) to five failed logins in five minutes. That limit is best effort: the address can be the proxy's, and one IPv6 /48 holds 65,536 /64 networks. The broker's two budgets are the real bound on guessing.

The session cookie is sent by the browser to every service on the same host name, whatever its port. Reach the page under a name or an address that no other service of yours is reached by.

## The certificate

The page is served over HTTPS only. "generate" makes a self-signed certificate (EC P-256, valid 825 days, for serving only) whose names are `localhost`, `127.0.0.1`, the listen addresses and the names you gave. A browser does not know it: the first visit shows a warning. Compare the SHA-256 fingerprint the browser shows for the certificate with the one `webui setup` and `webui status` print; only when they are equal is it your web UI. Alternatively import `.sdp/webui/tls/cert.pem` into the browser's or the system's trusted certificates, or give `webui setup` a certificate of your own (from your tailnet or your own certificate authority), whose names must include the names and addresses you browse to. The page sends no `Strict-Transport-Security` header, so a browser does not pin the name to a certificate that may change at the next setup.

To change the port, addresses, names or certificate: `sdp.py webui stop`, `sdp.py webui setup`, `sdp.py webui start`.

## What the container holds and what it does not

| It has | It does not have |
|---------|------------------|
| The broker's socket folder (`.sdp/socket`), mounted read-only at `/run/sdp`: it can connect to the socket, not remove or create anything there | The Docker socket, the deployment folder, `.env`, any database password, the broker's own folder, the scheduler's job store (`data/jobs` itself) |
| When they pass their checks at the start: the scheduler's control folder (`data/jobs/control`) read-only at `/run/sdp-jobs`, and its results folder read-only at `/run/sdp-results` | A way to write into either |
| When it passes its check at the start: the chat's socket folder (`.sdp/chat/socket`) read-only at `/run/sdp-chat` | The chat's work folder, its credential or settings |
| The certificate folder (`.sdp/webui/tls`), mounted read-only at `/tls` | Any other mount; a writable root file system (only a 16 MiB `/tmp` without exec) |
| The broker's client and the web package, and FastAPI, Jinja2 and uvicorn | The CLI, the verb registry, the setup code, PyYAML |
| The operator's user and group id, no capabilities, no new privileges, at most 256 processes and 512 MiB; two listening ports, 8443 and 8444 | A way out to the internet: its network does no masquerading, so it reaches the machine and nothing beyond |

The image pins htmx 2.0.4 and Pico CSS 2.1.1 and checks them against SHA-256 sums written in `Dockerfile.webui` when it is built. Its Python packages (FastAPI, uvicorn, Jinja2) are installed from PyPI with lower bounds in `requirements-webui.txt`, not pinned to versions or checked against hashes, as elsewhere in this project; only the two static files are checked against recorded sums.

Files on the host, in the deployment folder: `.sdp/webui/` (mode 0700) with `config.json` (0600: the port, addresses, names, the certificate's fingerprint and end date) and `tls/` (0700) with `cert.pem` and `key.pem` (0600).

## Sessions

A login sends the management password to the broker and keeps nothing of it. The broker's session token stays in the web UI's memory; the browser gets only a random session id in a cookie (`__Host-sdp_session`: HTTPS only, not readable by scripts, not sent by other sites, gone when the browser closes). Every form that changes something carries the session's form token, one per session; a choice that is taken is answered with a redirect, so a reload never sends it again. A session lasts as long as the broker's (at most eight hours) and ends at the logout, when the broker ends it (the password was changed, the broker was restarted) and when the broker cannot be reached; the login page then says why. A page or an action asks the broker on its way, so a session the broker has ended is found out at the next one: every Management page reads through the broker, every page of the Queue window asks it (its yes is believed for 5 seconds, a download asks every time), and every change of the Queue asks it before the scheduler. The logout is passed on to the broker under a bound of its own; when that stays full for a few seconds, the page says that the broker could not be told, and the broker's session then ends by itself within eight hours (its token was only in the web UI's memory, which drops it). Restarting the web UI logs everyone out.

A request body has ten seconds to arrive in full (408 beyond). Slow request headers are bounded only by the server's limit of 256 connections at a time. Every answer of the application carries the security headers described here; two answers come from the server itself and carry only its fixed text: its 503 when that limit is reached, and its 400 for a request it cannot parse.

## What it defends against, and what not

The web UI is written for these threats:

- **Anyone who can reach an address it answers on, without the password.** Nothing but the login page, the health check and the static files is served without a session; failed logins are limited by the broker's two budgets and, best effort, per address; requests over 64 KiB and anything but form data are refused before they are read.
- **A page of another site open in your browser.** Every request that is not a GET must come from the page itself (its `Origin`), and a logged-in request must also carry the session's form token; the page cannot be framed; a foreign `Host` is refused.
- **Hostile text shown on the page** (a source name, a file name, Docker's output). Everything is escaped, the page runs no inline script and allows no script but its own, and a name becomes a link only when it is a plain name.
- **A stolen cookie.** It works only from a browser that can reach the page, only until the logout or the session's end, and only for what the broker lets a session do (typed verbs; the management password again for a database start, a database reset, removing a database, the MCP servers' configuration or the scheduler's configuration, removing a source, and keeping the database admin password for the session) and for the Queue's actions, which a session the broker has ended cannot make. With it, an approval, a rejection, a kill and an EXPLAIN need no password; switching auto-accept on or raising its limit does.
- **A taken-over web UI process** (someone who gets to run code in it). Such a process holds the broker token of every live session, and reads every management password typed into the page after the takeover, which opens new logins and the verbs that need the password again. When the Queue's folders are mounted it can also ask the scheduler's control socket anything the socket takes (approve any pending query, switch auto-accept on) and read the results. It can probably reach services of this machine that listen on all of its addresses through its network's gateway: the databases, the MCP servers and the scheduler's page are published that way. What stays out of its reach: the Docker socket, the deployment's files, the internet, and anything the broker's typed verbs do not allow.

It does not defend against someone who can run programs on the host as you (that already has Docker and the files), nor against someone who has your management password. "Local" logins are those from anyone on this machine, other accounts included.
